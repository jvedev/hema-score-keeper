# New Competition Admin App (Phase 6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the single-page `apps/competition-admin` with the designed admin app: sign in, a "Needs you" list that only appears when something needs the admin, competitions grouped by lifecycle, and a competition page with Participants (participants → fighter → bout drill-down, reusing phase 4 views), objection review (restore / correct / void) and Settings (lifecycle, scope, ruleset parameters, "accept other bouts", co-admins, enrolling fighters). Laptop sidebar layout, phone bottom tabs, dark theme, English and Dutch.

**Architecture:** The app is a thin shell: a typed API client, a tiny path router, a layout shell, and screens that map API data onto `packages/ui` views. Three new reusable views go into `packages/ui` (`competition-list`, `needs-you-list`, `objection-review`); everything else reuses phase 4/5 views. Pure mapping functions (API → view models) live in `apps/competition-admin/src/mappers/` and are unit-tested in Node; screens are checked in the browser. Two small backend additions feed the screens.

**Tech Stack:** Vite app (vanilla TS), custom elements from `@hema/ui`, Vitest (Node for mappers/client, browser mode for views), Fastify backend tests.

**Spec:** `docs/superpowers/specs/2026-10-19-competition-admin-design.md` sections 5.1–5.7, 6, 7 (5.4 Board and 5.7 Video come in phases 8 and 9).

## Scope calls (Claude's, for the user to check)

- **Not in this phase:** Board (phase 8), sign-up approvals (needs the participant app's enrolment, phase 7), Video settings (phase 9), a personal **ruleset library** (spec §9). Rulesets stay what the backend has today: one ruleset per competition, edited as match parameters in Settings while the competition is Draft or Registration open.
- **Needs you** in this phase lists: open objections (with how long they've been open) and bouts still waiting for referee approval (with how long, no "Remind" yet — reminders need notifications, phase 8).
- **Correcting a bout** edits the final score of each fighter and the winner (or draw). The app keeps the original exchanges and appends one `ADJUSTMENT` exchange per changed fighter so the exchange list still adds up. Editing individual exchanges is left for later.
- **Fighters page** (sidebar item) is left out; fighters are managed per competition under Settings → Participants. The sidebar shows: Needs you · Competitions.
- The old `apps/competition-admin` code (clubs/users forms) is removed; club and user management stay available through the existing API for system admins (no UI in this phase).

## Global Constraints

- Work on `master`; commit only when the user asks. Bash, not PowerShell. Backend tests never open `data/dev.db`; browser checks run the backend on a seeded **copy** (`.superpowers/verify/`), as in phase 5.
- Views follow phase 4 conventions (data in, events out, frame built once, delegated listeners, escaped data, `aria-current` for selection, EN/NL via `t()`, `:host([hidden])` respected).
- Layout: sidebar at ≥ 900px viewport width, bottom tabs below; the "Needs you" nav item and tab exist only while it has items; the app opens on Needs you when it has items, else on Competitions.
- Competitions list order: Draft, Registration open, Running, Closed, Archived (Archived folded behind "Show n archived").
- Admin sees only competitions from `GET /api/v1/competitions/admin` (owner/co-admin; all for system admins).

## Review Focus

- An admin with nothing to do never sees an empty "Needs you" screen or tab, and lands on Competitions. → Task 6 test `opens on competitions when nothing needs you`.
- A correction to 4–4 on a bout that was 4–6 produces a valid backend request (draw, scores equal, ADJUSTMENT −2 for B) and the bout goes back to Counted with a new three-day window. → Task 3 test `correction becomes adjustments`, Task 5 browser check.
- Changing match parameters on a Running competition is impossible in the UI (fields disabled with the reason), and the backend refusal is shown if it happens anyway. → Task 7 test `ruleset locked once running`.
- Legacy bouts (no officials, no exchanges) open in bout details without errors. → Task 3 test `legacy bout details`.
- A co-admin sees Settings but can't add co-admins or transfer ownership (buttons absent), matching the backend's 403s. → Task 7 test `co-admin can't manage admins`.

### Task 2: UI views `competition-list` and `needs-you-list`

**Files:** scaffold both in `packages/ui/src/components/`; models + messages.

**Interfaces:**
```ts
export interface CompetitionListItemView { id: string; name: string; status: "DRAFT" | "REGISTRATION_OPEN" | "RUNNING" | "CLOSED" | "ARCHIVED"; scopeLabel: string; meta: string; openBouts: number }
export interface NeedsYouItemView { kind: "objection" | "awaiting-referee"; boutId: string; competitionName: string; fighterA: string; fighterB: string; scoreA: number; scoreB: number; detail: string; since: string }
```

### Task 3: UI view `objection-review` and correction helper

**Files:** scaffold `packages/ui/src/components/objection-review/*`; `packages/match-engine/src/correction.ts` (+ test) for the pure correction maths.

**Interfaces:**
```ts
// match-engine
export function correctionExchanges(
  original: { scoreA: number; scoreB: number },
  corrected: { scoreA: number; scoreB: number },
  atSeconds: number,
): Array<{ atSeconds: number; kind: "ADJUSTMENT"; side: "A" | "B"; points: number; reason: string }>;   // one per changed side, reason "Corrected after objection"
```
- `<objection-review>`: property `bout: BoutDetailView` (phase 4 model) plus `objection: { by: "A" | "B"; reason: string | null; objectedAt: string }`; renders the bout (reusing `<bout-details>` with warnings shown), the objection, and three actions: **Restore** (keep the result), **Correct** (inline score inputs per fighter + winner select A/B/Draw, validated: winner must not have the lower score, draw needs equal scores), **Void** (reason required). Events `objection-restore-requested`, `objection-correct-requested {scoreA, scoreB, winnerSide}`, `objection-void-requested {reason}`. `setBusy(boolean)`, `setError(message|null)`.

- [ ] **Step 1: Failing tests:** **`correction becomes adjustments`** (4–6 → 4–4 gives one ADJUSTMENT B −2; 4–6 → 6–4 gives A +2 and B −2; unchanged → none); view: restore fires once; correct with 4–4 + draw fires `{4,4,null}`; correct with winner A at 4–6 shows the validation hint and fires nothing; void needs a reason; busy disables all actions; **`legacy bout details`** (a `BoutDetailView` with no officials' jury/table, empty exchanges renders without errors); Dutch labels.
- [ ] **Step 2–4:** run → FAIL; implement; run tests + typecheck → PASS.
